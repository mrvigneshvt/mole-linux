# Known gaps

- **Most product behavior remains scaffolded.** The Rust toolchain is available; issue #30 builds, passes clippy and tests, and its read-only snapshot CLI was exercised. Evidence: [STATUS.md](STATUS.md), `../../Cargo.toml`, `../../src/main.rs`, `../../src/snapshots.rs`.
- **Live snapshot contents are unverified on the current host (2026-10-19).** The read-only `btrfs subvolume list /` probe reports `Operation not permitted`; `snapper list` reports `No permissions.` The user reports `/.snapshots` is root-owned mode 0750. Both are presented as unavailable with self-run sudo guidance. Shim output, argv, successful listing parsing, and permission handling are covered by `../../tests/snapshots.rs`.
- **Research coverage is bounded.** The [upstream review](research/mole-upstream-review.md) inventories the pinned main tree and inspects subsystem flows/representative tests. It is not a line-by-line security audit, passing-suite claim, review of the Windows branch/private native apps, or complete issue/history review. macOS runtime behavior is unverified here.
- **Advantages remain proposals.** Linux adapters, filesystem accounting, recovery and approved-plan execution are not implemented or benchmarked. Exact reclaimable space and general undo must not be promised. Product scope and acceptance criteria require agreement. Evidence: [research](research/mole-upstream-review.md).
- **License chosen (GPL-3.0, 2026-10-19); manifest and name not yet updated.** `Cargo.toml` now `GPL-3.0-only`; LICENSE text file not yet added. Name `mole-linux` must change before public release per upstream TRADEMARK.md. Evidence: [decision](decisions/2026-10-19-v1-scope.md), [naming/reuse section](research/mole-upstream-review.md#naming-and-code-reuse-source-facts-decision-pending).
- **M1 TUI gaps (verified 2026-10-19).** Orchestrator drove the live TUI in tmux on `~/Workspace`: totals match `du -sB1` (allocated and apparent), descend/up/apparent toggle/`q` work, exit 0. Not verified: panic terminal restoration. Missing vs Mole: progressive results (list is empty until the scan completes; ~6s debug build vs `du` 2.4s on 10.7 GiB), no parallel scanning. Evidence: `../../src/tui.rs`, `../../src/scan.rs`.
- **M3.2 Trash deletion timestamps use UTC.** The current Rust standard library and approved rustix API do not expose local timezone conversion; timestamps remain valid ISO-like values but do not meet the freedesktop local-time requirement. `ponytail:` in `../../src/core/sink.rs` records the ceiling and upgrade path: add an approved libc-based timezone conversion. Evidence: `../../src/core/sink.rs` (`utc_timestamp`).
- **M3.2 bind-mount runtime verification deferred to #15.** Permanent directory removal checks both `st_dev` and `STATX_MNT_ID`, and refuses when the kernel omits the mount ID. Injected-ID decision tests pass; this runner cannot create an unprivileged nested bind mount, so the end-to-end bind-mount scenario remains for the #15 honeypot. Evidence: `../../src/core/sink.rs` (`Identity`, `remove_tree`), `../../tests/core_sink.rs`.
- **M7.1 configured purge roots outside HOME are deliberately refused.** Upstream `clean_project_artifacts` permits configured roots such as `/var/www`, but this Linux port keeps purge candidates inside the user's HOME because the current deletion validator and policy are home-scoped. This narrows reach and avoids adding a second authorization boundary to the sink. Evidence: `../../src/purge.rs` (`is_safe_project_artifact`, `is_safe_configured_artifact`), `../../tests/purge_paths.rs` (`configured_roots_outside_home_remain_refused`).
- **M7 installer ZIP inspection has a cumulative byte/count budget but no wall-clock timeout.** Standard-library file reads cannot be cancelled once blocked in filesystem I/O; discovery is bounded to 100,000 entries, 16 MiB per central directory, and 64 MiB cumulative central-directory data. Interruptible archive I/O remains an upgrade path. Evidence: `../../src/commands/installer.rs` (`ScanBudget`, `zip_has_installer`).

- **Arch package source integrity and build remain pending a release tag.** The recipe targets `v$pkgver`, but the repository currently has no tags; `makepkg --printsrcinfo` validates metadata only. The source checksum is `SKIP` until the matching release archive exists, so do not publish this recipe to AUR or claim a package build until the checksum is pinned and a full `makepkg` build passes. Evidence: `../../packaging/arch/PKGBUILD`, `../../tests/honeypot/scenarios/arch-package.sh`; repository tags checked with `git ls-remote --tags origin` on 2026-10-19.
- **M6.1 sudo authentication failure is reported as `Failed`, not `Unavailable`.** `sudo` exits 1 on a bad password, and an owner tool exiting 1 looks the same, so `OwnerRun` cannot tell them apart. Upgrade path: distinguish sudo's own failure (e.g. `sudo -v` before the action) without retrying. Evidence: `../../src/core/privilege.rs` (`OwnerRunner::run`).
- **M6.1 root refusal is enforced only in the binary entry point.** `ensure_not_root` runs at the top of `run()` in `../../src/main.rs`; library callers must check euid themselves. Live check: the release binary exits 2 as container root and runs as `mole`. Evidence: `../../tests/honeypot/docker/run.sh` (`privilege-sudo`).
- **M6.1 real-sudo coverage runs only in the honeypot container.** `privilege_honeypot` is `#[ignore]`d and needs passwordless sudo; it is not part of `cargo test`. Evidence: `../../tests/honeypot/scenarios/privilege-sudo.sh`.
- **M4.4 `project-pycache` is not registered in `clean`'s catalog.** `rules::clean::catalog()` stays empty because `tests/clean.rs:clean_accepts_rule_filters_and_records_a_zero_rule_preview` pins the empty catalog: once any rule is registered, `--select thumbnail-cache` is rejected as unknown. Until that test is updated by an owner decision (or M4.2 changes it), `mole-linux clean` does not clean `__pycache__`; the rule runs only through `execute_rules` in tests. Evidence: `../../src/rules/project_cache.rs`, `../../src/rules/clean.rs` (`catalog`), `../../tests/clean.rs`, `../../tests/project_cache.rs`.
- **M4.4 guard-kept caches are not listed.** Caches refused as `tracked by git` or `holds a nested git repository` are dropped from discovery silently; upstream logs them as SKIPPED to the operations log. Unanswerable checks are reported (Partial discovery), not dropped. Upgrade path: a `kept` list on `Discovery`. Evidence: `../../src/rules/project_cache.rs` (`discover`, `Guard`).
- **M4.4 `ponytail:` project cache walk bounds.** `MAX_DIRECTORIES` (200,000) and `MAX_TREE_ENTRIES` (100,000) replace upstream's 6-second `find` timeout; a root that exceeds them is reported Partial. Upgrade path: deadline-driven walk. Evidence: `../../src/rules/project_cache.rs`.
- **M4.4 `ponytail:` one `git ls-files` per candidate.** Upstream batches Git listings per repository (`project_cache_build_git_index`); per-candidate probes are slower on repositories with hundreds of caches. Upgrade path: per-repository tracked index. Evidence: `../../src/rules/project_cache.rs` (`GIT_BUDGET`), `../../src/purge.rs` (`has_tracked_files`).
- **M4.4 scope is `__pycache__` only.** Not ported from `lib/clean/caches.sh`: `.next/cache`, `.dart_tool` and `build/` (Flutter), and `clean_service_worker_cache` (ledger row lists it under M4.4 but it is browser/app profile data, so it belongs with M4.3). Evidence: `docs/agent-context/plans/PARITY-LEDGER.md` (`## lib/clean/caches.sh`).
- **M4.4 Trash recovery does not free space until Trash is emptied.** Regenerable caches go through the sink's Trash mode, not upstream's permanent `safe_remove`. On btrfs, and on any filesystem where Trash keeps the data, the statvfs delta shows no gain until emptying (M4.2 row). Evidence: `../../src/commands/clean.rs` (`RecoveryMode::Regenerate` → `DeleteMode::Trash`), `../../src/rules/project_cache.rs` (`candidate_for`).
- **M4.4 final guard and sink leave a small window.** Git and nested-repository state are re-read just before the sink, but a file tracked between that check and the sink's identity recheck is not seen. The sink revalidates identity and policy, not Git state. Evidence: `../../src/commands/clean.rs` (`final_guard_refusal`), `../../src/core/sink.rs` (`delete`).
- **Sink policy refuses `models` and `volumes` path components.** A project under a directory named `models` or `volumes` has its `__pycache__` refused by `validate.rs` as protected, reported as `policy`. Evidence: `../../src/core/validate.rs` (`check_policy`).
- **`tests/honeypot/docker/run.sh clean-dryrun` fails before the scenario asserts.** `run.sh` does not pass the binary path to `scenarios/clean-dryrun.sh`, which requires it (`${1:?}`), so the container run exits 1 with "pass the mole-linux binary path". The host test `clean_dryrun_scenario_keeps_every_honeypot_canary` passes the path and is green; the container path is pre-existing and was not changed by M4.4. Evidence: `../../tests/honeypot/docker/run.sh`, `../../tests/honeypot/scenarios/clean-dryrun.sh`.
- **M6.2 paccache apply re-computes its set.** Preview runs `paccache -dk3`/`-duk0`; apply runs `sudo -- paccache -rk3`/`-ruk0`, so the removed files are chosen at apply time, not the previewed files. `ponytail:` in `../../src/rules/system.rs` (`PaccacheRule::owner_command`). Evidence: `../../tests/honeypot/scenarios/clean-pacman-apply.sh`, `../../tests/clean_system.rs`.
- **M6.2 owner-native candidates skip the HOME policy and sink identity recheck.** Owner tools choose their own targets outside HOME (`/var/cache/pacman/pkg`), so only the whitelist and the owner-state recheck guard them. Owner actions have no per-item sizes, so the summed total is `unknown`. Evidence: `../../src/commands/clean.rs` (`protected_reason`, `execute_rules_with_owner`).
- **M6.2 statvfs delta is measured on HOME's filesystem only.** The honeypot run removed 2 MiB from `/var/cache/pacman/pkg` and reported `Measured statvfs free-space delta: +0 bytes`, because the probe reads HOME. Owner-native space on another mount will not show here. Upgrade path: measure each affected mount. Evidence: `../../src/commands/clean.rs` (`available_bytes`).
- **M6.2 AUR build-dir owner check covers `makepkg` only.** Discovery and apply check `makepkg`; a `yay` process started mid-run is not rechecked. `ponytail:` in `../../src/rules/system.rs` (`YayBuildRule::discover`). Evidence: `../../tests/clean_system.rs`.
- **M6.2 owner probe reads stdout whole.** `OwnerRunner::probe` buffers all stdout; paccache's dry-run summary is one line. `ponytail:` in `../../src/core/privilege.rs` (`OwnerRunner::probe`).
- **M6.2 `-duk0`/`-ruk0` and AUR build dirs are verified only by unit tests with fake tools and a temp HOME.** The Arch honeypot scenario covers only `pacman-cache-keep3`. Evidence: `../../tests/clean_system.rs`, `../../tests/honeypot/scenarios/clean-pacman-apply.sh`.
