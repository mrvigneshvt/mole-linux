# Upstream Mole: command lifecycle, maintenance and delivery

Reviewed 2026-10-19 against upstream commit `8c55e8c07f3b34eeeb0352753b660f823468cd43` (source version 1.61.0). Read-only source investigation; no upstream command, installer, maintenance action or test was executed. This is an area report, not a claim that every file in upstream was read line by line.

## Routing and process boundaries

`mo` is a seven-line wrapper that resolves its directory and execs `mole`. The main router rejects externally inherited root privileges before loading user-scoped state, checks whether the current working directory still exists, resolves its own installation through symlinks, extracts global `--debug`, then routes commands. It accepts `analyse`/`optimise` aliases. An empty command starts the interactive menu; explicit commands dispatch to their entry scripts. `history` is dispatched *before* `common.sh` loads, preserving a read-only log path without initializing normal cleanup state. Update and remove functions are sourced for use by both the menu and explicit commands. [Router and early history](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/mole#L1-L139), [command dispatch](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/mole#L303-L435).

The update wrapper distinguishes interactive human output from help, redirected output and automation. Its comments and implementation explicitly preserve signal/terminal behavior while arranging background update notices. This is complexity to avoid recreating unnecessarily in a single Rust executable. [Wrapper](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/manage/update.sh#L923-L1015).

## Optimize is bounded maintenance, not a generic speed button

The flow is: parse flags → start an operation-log session → gather and minimally validate health JSON → load optimize exclusions → run diagnostics → request admin consent once → dispatch every catalog entry → require a recorded outcome for every task → show summary → return failure if any task failed. Dry runs do not acquire admin credentials. Admin refusal skips privileged work rather than repeatedly prompting. Session cleanup logs applied and failed tasks and handles interruption. [Entrypoint](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/bin/optimize.sh#L175-L336).

The catalog registers **19** tasks and validates IDs, handler uniqueness, aligned metadata and automatic-execution eligibility. They cover Finder caches, saved state, broken preferences, DNS, SQLite vacuum, Finder `.DS_Store` preferences, legacy overrides, network stack, permissions, Spotlight, periodic jobs, shared file lists, disk verification, login items, quarantine history, launch agents, notifications and CoreDuet. This is overwhelmingly macOS policy; the portable asset is the explicit task contract, not the targets. [Catalog](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/optimize/catalog.sh).

Every dispatched task must record exactly one outcome: `applied`, `unchanged`, `skipped`, `unavailable`, `attention`, or `failed`. Missing results, duplicate results and invalid transitions are errors. A task that partially changes state but encounters an eligible failure is failed; attention alone does not fail the run. Exclusions are resolved by action identity, with a legacy DNS opt-out alias maintained. [Outcome state machine](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/optimize/outcomes.sh), [dispatcher](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/optimize/tasks.sh#L2069-L2104).

Task source inspection confirms checks around active apps, SQLite integrity and free pages, VPN uncertainty, Spotlight probes, and bounded disk verification. These are examples of capability and liveness checks; they do not prove a general claim that maintenance cannot lose data. `tasks.sh` is over 2,000 lines and was inspected by function inventory plus selected paths, not exhaustively audited here. [SQLite path](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/optimize/tasks.sh#L504-L695), [disk verification](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/optimize/tasks.sh#L1470-L1511).

## History and shell integration

`mo history` supports text/JSON and a validated limit of 1–200 (default 20). It reconstructs sessions from operations.log and reads deletion records from a TSV log. Logs default to `~/Library/Logs/mole/`. Missing files are handled without creating them. Rendering is limited, but the loaders read the complete files into arrays: the CLI limit is not a bound on input loading or memory. History is audit visibility, not an undo engine. [CLI](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/bin/history.sh), [loaders](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/core/history.sh#L514-L549), [JSON shape](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/core/history.sh#L802-L822).

Completion generates Bash, Zsh and Fish definitions for both command names. Without a shell argument it can install shell integration; `--dry-run` previews writes. It shares the command catalog and resolves dotfile symlink chains, refusing broken/cyclic chains rather than rewriting them. Removal uses the corresponding exact marker pattern. Linux should offer generated completions first; automatic rc editing adds lifecycle responsibility. [Completion source](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/bin/completion.sh#L1-L115), [removal integration](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/manage/remove.sh#L41-L127).

`touchid` is a distinct macOS authentication-configuration feature, not disk cleanup. It checks hardware capability, manages `pam_tid.so` in sudo/sudo_local, supports status/enable/disable and dry run, makes backups on relevant legacy branches, and installs PAM files as root-owned mode 444. It should not be translated into automatic Linux fingerprint/PAM changes: this adds authentication risk outside the Linux project's current purpose. [Touch ID](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/bin/touchid.sh).

## Installation, updating and removal

The installer explicitly refuses non-Darwin hosts and macOS below 12. It detects the active Homebrew installation without uninstalling another copy that happens to coexist. Manual installs separate launchers and configuration/resources, pin the resource path in the router and install per-architecture Go helpers. [Requirements](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/install.sh#L1191-L1258).

Downloaded helpers are staged, checked against SHA256SUMS, and moved into place. A downloaded asset with missing/mismatching checksums or failed attestation aborts; it does not silently downgrade to source build. Network unavailability has different fallback behavior, including another release or local build. Local/source builds are separate trust paths. This integrity distinction is worth preserving. [Binary acquisition](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/install.sh#L1321-L1439).

Attestation verifies SHA256SUMS with `gh attestation verify --repo tw93/Mole --deny-self-hosted-runners`. If `gh` is missing or unauthenticated, default behavior permits checksum-only verification; `MOLE_REQUIRE_ATTESTATION=1` makes that unavailable verification fatal. Do not describe upstream as universally requiring signed provenance. Checksums downloaded from the same release are integrity evidence but alone do not add an independent trust anchor. [Actual policy](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/install.sh#L888-L1016).

Installation has target-adjacent writer locks, ownership/ancestor checks and a kernel-lock/atomic-mkdir fallback. Launchers are individually copied to `.new` and renamed, but the shell/lib tree is copied separately, so this is **not a whole-generation atomic deployment**. An incomplete-helper marker and bounded installed version/help checks detect important partial installs. Update additionally verifies its unique receipt, channel, expected version/commit and installation state under the lock before announcing success. [Install locks](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/install.sh#L291-L650), [installation](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/install.sh#L1442-L1602), [receipt verification](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/manage/update.sh#L367-L446).

Update/removal detect the invoked installation rather than guessing from PATH. Nix-store installations are identified separately. Removal checks launcher contents rather than trusting the basename `mo`, previews removals, keeps operation logs, removes its own completion integration and preserves non-default config roots for manual review. This is useful ownership discipline for Linux package-manager coexistence. [Install detection](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/manage/update.sh#L611-L746), [self-removal](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/lib/manage/remove.sh).

## Build, CI and release integrity

Release workflow builds Darwin amd64/arm64 analyze/status binaries, checks source/tag agreement and minimum macOS deployment targets, emits checksums and GitHub build-provenance attestations, publishes assets, then opens/verifies the Homebrew Core formula update. Publication requires completed successful Check, Validation, CodeQL and Nix runs for the tagged commit, with an explicit docs-only inheritance rule. Missing/cancelled runs do not count as green. Workflow action references use commit pins. This describes checked-in workflow behavior, **not evidence that a particular current release or CI run passed**. [Release workflow](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/.github/workflows/release.yml).

Nix packages only `aarch64-darwin` and `x86_64-darwin`; it intentionally preserves system shebangs/BSD tools and disables package-level tests (`doCheck = false`). Its CI checks formatting/package construction, installed layout, and profile install/upgrade/removal. Nix support must not be mistaken for Linux/NixOS runtime support. [Package](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/package.nix), [flake](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/flake.nix), [Nix workflow](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/.github/workflows/nix.yml).

Validation combines Bats, Go tests, PTY tests through owning suites, performance budgets, high-risk path regression tests and secret scanning. Full validation uses macos-latest, with a selected compatibility subset on macOS 15/26; this does not prove all supported macOS versions at runtime. `scripts/test.sh` forces no-auth testing and can skip optional suites/tools, so a local success needs its skip summary read. [Validation workflow](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/.github/workflows/test.yml), [test runner](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/scripts/test.sh).

Source audits enforce destructive-sink annotations, reject test assertions that cannot fail under Bash 3.2, flag structurally duplicate shell helpers and centralize timeout-status interpretation. The destructive audit recognizes recursive-force rm/find-delete patterns; it requires a comment, not proof that a sink is safe, and is not a comprehensive shell semantics analyzer. Bundle-drift auditing compares the real host's app inventory with protection data and explicitly requests human classification. [Checks](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/scripts/check.sh#L210-L250), [sink audit](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/scripts/audit_destructive_sinks.py), [bundle audit](https://github.com/tw93/Mole/blob/8c55e8c07f3b34eeeb0352753b660f823468cd43/scripts/audit_bundle_drift.sh).

## Linux opportunities, proposed rather than implemented

1. **One inspectable transaction:** scan → explicit candidates with ownership/rebuild cost/reason → reviewed plan → fresh validation → action → per-item receipt. The receipt should distinguish removed, moved to Trash, retained, failed and space actually recovered. Upstream already has dry run/logging; the opportunity is connecting review and execution with one stable, machine-readable plan.
2. **Distribution ownership:** prefer package-manager-owned installation/update/removal; never overwrite packaged files through self-update. Ship an initial Arch package before promising universal distro behavior. A single Rust binary can avoid mixed shell/helper generations.
3. **Honest reclaimed-space reporting:** expose logical size versus allocated/reclaimable estimates, retained/open-deleted files, and snapshot/shared-extent uncertainty. Do not claim a byte counter proves freed capacity. Linux-specific mechanisms need a separate primary-source investigation before specification.
4. **Capability-aware maintenance:** start read-only and narrow. Reuse the six-state outcome idea, show unavailable capabilities explicitly, and avoid a catch-all optimize command that changes networking, permissions or authentication without an individually justified problem.
5. **Bounded audit history:** structured versioned records, bounded loading/retention, control-byte-safe rendering, and a real restore ledger for actions that are reversible. Upstream history is useful, but restore requires additional state and policy, not just a button over a log.

These are product hypotheses, not evidence of superiority. Compare measurable safety, plan clarity and actual reclaimed bytes on realistic Linux fixtures before making that claim.
